Module 46: REST APIs for SAP — Building RESTful and Streaming APIs with ABAP

For beginners: REST (Representational State Transfer) is a way to expose and consume APIs over HTTP: clients send GET (read), POST (create), PUT/PATCH (update), DELETE to URLs (resources). SAP exposes many REST-style APIs via OData (SAP Gateway). You can also build your own REST and streaming APIs in ABAP—either as OData services (Gateway) or as custom HTTP handlers. This chapter shows how REST fits into SAP and how to implement RESTful and streaming APIs with ABAP code. Key terms: REST, OData, SAP Gateway, ICF, streaming.

REST APIs in SAP are the main way for Fiori, mobile apps, and external systems to read and write business data. OData (used by SAP Gateway) is REST-based; you can also build custom REST and streaming endpoints in ABAP.

REST APIs in SAP — overview

SAP delivers and lets you build REST-style APIs in several ways:

  • SAP Gateway / OData: Gateway exposes OData v2/v4 services. OData is RESTful: resources (entity sets) are accessed via URLs; HTTP methods map to read (GET), create (POST), update (PUT/PATCH), delete (DELETE). S/4HANA ships many prepackaged OData services (API Business Hub); you can create custom ones with SEGW (Service Builder) and implement the data provider in ABAP.
  • S/4HANA released APIs: Hundreds of OData and REST APIs are released for cloud and on-premise (e.g. Sales Order API, Business Partner API). These are the preferred way for external and BTP apps to talk to S/4HANA (clean core).
  • Custom REST in ABAP: Using ICF (Internet Communication Framework), you register a handler class that implements IF_HTTP_EXTENSION. The handler receives the HTTP request (method, path, body) and writes the response (status, headers, JSON body). This gives full control for custom REST or streaming responses.
  • BTP / API Management: BTP can host APIs (e.g. ABAP Cloud) and API Management can expose and secure S/4HANA OData/REST. See Module 22 and Module 29.

Building RESTful APIs with ABAP

Two main options: (1) OData via SAP Gateway (SEGW) — define entity sets and implement the Data Provider Extension (DPC_EXT); (2) Custom ICF handler — implement IF_HTTP_EXTENSION~HANDLE_REQUEST, parse path/method, and return JSON. Below are code examples for both.

Option 1: OData service (Gateway) — GET entity set

In SEGW you define an entity set (e.g. BillingSet with entity type from VBRK). The framework generates a DPC (Data Provider Class) and DPC_EXT. You implement GET_ENTITYSET in the DPC_EXT to read from tables and fill the response. OData then exposes it as a REST resource (e.g. GET /sap/opu/odata/sap/ZBILLING_SRV/BillingSet).

ABAP: Data Provider Extension — GET_ENTITYSET for billing documents (conceptual; method signature may vary by Gateway version):

METHOD billingset_get_entityset.
  DATA: lt_vbrk TYPE TABLE OF vbrk,
        ls_entity TYPE zcl_xxx_mpc=>ts_billing,
        lt_entity TYPE zcl_xxx_mpc=>tt_billing.

  " Read filter parameters from request (e.g. date range)
  DATA(lo_filter) = io_tech_request_context->get_filter( ).
  " ... evaluate filter, then SELECT

  SELECT vbeln, fkdat, kunag, netwr, waerk
    FROM vbrk
    INTO TABLE @lt_vbrk
    UP TO 100 ROWS
    WHERE fkdat >= @sy-datum - 30.

  LOOP AT lt_vbrk INTO DATA(ls_vbrk).
    ls_entity-vbeln    = ls_vbrk-vbeln.
    ls_entity-fkdat    = ls_vbrk-fkdat.
    ls_entity-kunag    = ls_vbrk-kunag.
    ls_entity-netwr    = ls_vbrk-netwr.
    ls_entity-waerk    = ls_vbrk-waerk.
    APPEND ls_entity TO lt_entity.
  ENDLOOP.

  copy_data_to_ref( EXPORTING is_data = lt_entity
                    CHANGING  cr_data = er_entityset ).
ENDMETHOD.

Option 2: Custom REST handler (ICF)

Register an ICF service (SMICM → ICF) and assign a handler class. The class implements IF_HTTP_EXTENSION. In HANDLE_REQUEST you read the request (method, URI, body), run your logic (e.g. SELECT from VBRK), build JSON, and write it to the response. This is a full REST endpoint without OData.

ABAP: Custom REST handler class (complete example):

CLASS zcl_rest_billing DEFINITION PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_http_extension.
ENDCLASS.

CLASS zcl_rest_billing IMPLEMENTATION.
  METHOD if_http_extension~handle_request.
    DATA: lo_request  TYPE REF TO if_http_request,
          lo_response TYPE REF TO if_http_response,
          lt_vbrk     TYPE TABLE OF vbrk,
          lv_json     TYPE string.

    lo_request  = server->request.
    lo_response = server->response.

    CASE lo_request->get_method( ).
      WHEN 'GET'.
        SELECT vbeln, fkdat, kunag, netwr, waerk
          FROM vbrk
          INTO TABLE @lt_vbrk
          UP TO 100 ROWS
          WHERE fkdat >= @sy-datum - 30.

        " Build JSON (use /ui2/cl_json or similar, or manual concatenation)
        " Example: use CL_TREX_JSON_SERIALIZER or /UI2/CL_JSON
        /ui2/cl_json=>serialize( EXPORTING data = lt_vbrk
                                 CHANGING  r_json = lv_json ).

        lo_response->set_status( 200 ).
        lo_response->set_header_field( i_name  = 'Content-Type'
                                       i_value = 'application/json' ).
        lo_response->set_cdata( lv_json ).
      WHEN OTHERS.
        lo_response->set_status( 405 ).
        lo_response->set_cdata( '{"error":"Method not allowed"}' ).
    ENDCASE.
  ENDMETHOD.
ENDCLASS.

After implementing the class, create an ICF node (e.g. path /sap/z_rest_billing) and assign the handler class. The endpoint is then GET https://<host>/sap/z_rest_billing returning JSON.

Streaming APIs with ABAP

Streaming means sending the response in chunks instead of building the whole payload in memory. Use cases: large result sets, server-sent events (SSE), or NDJSON (newline-delimited JSON) for real-time feeds. In ABAP you write to the HTTP response in chunks by flushing parts of the body as you generate them.

  • Chunked transfer: Set Transfer-Encoding: chunked. Write segments to the response; the framework sends each segment as a chunk. The client can process data as it arrives.
  • NDJSON: Send one JSON object per line. Each line is a valid JSON object; the client reads line by line. Good for logs, events, or large lists.

Streaming response example (chunked NDJSON)

Below, the handler opens the response for streaming, sets headers for JSON and chunked encoding, then loops over a large SELECT and writes one JSON line per row. Each flush (or writing to the stream) sends a chunk. This keeps memory usage low and allows the client to consume rows as they arrive.

ABAP: Streaming GET — write NDJSON chunks to response:

METHOD if_http_extension~handle_request.
  DATA: lo_request   TYPE REF TO if_http_request,
        lo_response  TYPE REF TO if_http_response,
        lo_stream    TYPE REF TO if_http_entity,
        lv_json_line TYPE string,
        lv_crlf      TYPE string VALUE cl_abap_char_utilities=>cr_lf.

  lo_request  = server->request.
  lo_response = server->response.

  IF lo_request->get_method( ) <> 'GET'.
    lo_response->set_status( 405 ).
    lo_response->set_cdata( '{"error":"Method not allowed"}' ).
    RETURN.
  ENDIF.

  lo_response->set_status( 200 ).
  lo_response->set_header_field( i_name  = 'Content-Type'
                                 i_value = 'application/x-ndjson' ).
  " Chunked transfer: do not set Content-Length; server sends chunked
  lo_stream = lo_response->get_entity( ).

  " Use open write stream (implementation may use response->get_entity( ) and write in chunks)
  " Pseudocode: open stream, then in loop:
  SELECT vbeln, fkdat, kunag, netwr
    FROM vbrk
    WHERE fkdat >= @sy-datum - 30
    INTO @DATA(ls_vbrk).
    /ui2/cl_json=>serialize( EXPORTING data = ls_vbrk
                             CHANGING  r_json = lv_json_line ).
    lo_stream->append_cdata( lv_json_line ).
    lo_stream->append_cdata( lv_crlf ).
    " Flush periodically if supported (e.g. every N rows) so client receives chunks
  ENDSELECT.
ENDMETHOD.

In practice, whether chunked flush is automatic or explicit depends on the ICF/Web Dispatcher version. For true streaming, ensure the response is not buffered entirely and that the client uses HTTP chunked encoding. ABAP 7.5+ and S/4HANA support writing to the response entity in a streaming fashion; check the documentation for IF_HTTP_ENTITY and chunked output in your release.

Key concepts

REST: Architectural style over HTTP — resources (URLs), methods (GET/POST/PUT/DELETE), stateless. OData: Protocol built on REST; SAP Gateway exposes OData. ICF: Internet Communication Framework — registers HTTP handlers in SAP. Streaming: Sending response in chunks (chunked transfer) so the client can process data incrementally; NDJSON is one format.

Module Quiz

Q1: In SAP, REST-style APIs are most commonly exposed via:

  • A) IDoc only
  • B) OData (SAP Gateway) and custom ICF handlers
  • C) Only CPI
  • D) Only BAPI
Correct: B
OData via Gateway is the standard RESTful API in SAP; custom REST can be built with ICF and IF_HTTP_EXTENSION.

Q2: For a custom REST endpoint in ABAP (no OData), you implement:

  • A) Only SE38 report
  • B) A class implementing IF_HTTP_EXTENSION, registered in ICF
  • C) Only BAPI
  • D) Only IDoc
Correct: B
ICF handler class implementing IF_HTTP_EXTENSION~HANDLE_REQUEST processes the HTTP request and writes the response.

Q3: Streaming APIs are useful when:

  • A) You only need one record
  • B) You need to send large or continuous data in chunks so the client can process incrementally
  • C) You only use GET
  • D) You do not use JSON
Correct: B
Streaming (chunked transfer, NDJSON) sends data in segments, reducing memory and enabling real-time or large payloads.
