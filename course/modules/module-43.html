Module 43: SAP HANA (Platform)

For beginners: SAP HANA is SAP’s in-memory database and platform. “In-memory” means data is stored primarily in RAM (random access memory) instead of only on disk, which allows very fast reads and writes. HANA is the required database for S/4HANA, BW/4HANA, and many other SAP products. It also offers advanced capabilities: columnar storage for analytics, built-in analytics (e.g. calculation views), and an application server (XS/XSA) for running lightweight apps. Key terms: in-memory, column store, row store, calculation view, S/4HANA.

HANA was designed for both transactional (OLTP) and analytical (OLAP) workloads. S/4HANA runs only on HANA; the simplified data model and real-time reporting in S/4HANA depend on HANA’s speed and columnar storage. HANA is available on‑premise (hardware or certified appliances) and in the cloud (SAP HANA Cloud).

Purpose and scope

Database: Store and retrieve data with high throughput and low latency. Support for SQL, full ACID transactions. Used by S/4HANA, BW/4HANA, and custom applications. Storage: Data can be stored in row store (good for single-row operations, e.g. “get one order”) or column store (good for aggregations and scans, e.g. “sum revenue by region”). Many tables use column store by default. In-memory: Hot data resides in memory; cold data can be tiered to disk (e.g. HANA extended storage). Persistence to disk still exists for durability. Advanced analytics: Calculation views (graphical or SQL-based) for multi-table logic and aggregations; can be consumed by reporting tools. Text search, spatial, and graph capabilities. Application layer: SAP HANA XS/XSA (extended application services) for running small apps and services on the same platform (less common now with BTP).

In plain terms: Column store stores data by column (all “revenue” values together) instead of by row (one row = one order with many columns). When you run “sum(revenue) by region,” the database only reads the revenue and region columns and can compress them heavily—so analytics run much faster. Row store is better when you often read or update one full row (e.g. one sales order document).

Features in detail

  • Columnar storage and compression: Column store tables compress very well (similar values in a column). Aggregations (SUM, COUNT, AVG) and filters on columns are fast. HANA automatically chooses row vs column for optimal performance; application tables in S/4HANA use both (e.g. header row store, line item column store).
  • Calculation views: Built in SAP HANA Studio or Web IDE. Combine tables, add joins, filters, and calculated columns. Expose as consumption models for reporting (e.g. from SAC, BW, or Fiori). Support for hierarchy, variables, and input parameters. Enable “push-down” of logic to the database so only result set is sent to the client.
  • SQL and scripting: Native SQL (SQLScript) for complex logic; procedures and functions. Used by ABAP (e.g. CDS views with HANA-specific optimisations) and by BW/4HANA. Full SQL standard support plus HANA extensions.
  • High availability and scale-out: Multiple nodes (scale-out) for very large databases. Replication (e.g. system replication) for disaster recovery. Backup and recovery (snapshots, log backup).
  • SAP HANA Cloud: HANA as a managed service in the cloud (SAP BTP or hyperscaler). Same engine; no customer-managed infrastructure. Used by S/4HANA Cloud and other SAP cloud services. Smaller footprint options (e.g. HANA Cloud for development and mid-size).

Data plane and control plane

Data plane: Data is stored in HANA tables (row or column). S/4HANA application tables (e.g. ACDOCA, VBAK, VBAP) live in HANA. Logs and persistence ensure durability. Calculation views and virtual tables (e.g. to remote sources) are metadata and definitions. Control plane: Database administration: create schemas, users, roles; monitor memory, CPU, and disk; tune parameters. Backup and recovery configuration. In S/4HANA, much of this is done via the application layer (Basis); standalone HANA (e.g. for BW/4HANA or custom) is administered via SAP HANA Cockpit or Studio. No SPRO—HANA is the database; configuration of the SAP application (S/4HANA) is in the application.

Deployment and integration

Deployment: On‑premise: HANA on certified hardware (e.g. SAP HANA Appliances) or supported virtualised environments. S/4HANA and BW/4HANA run on top. Cloud: SAP HANA Cloud (managed by SAP) or HANA on hyperscaler (e.g. AWS, Azure, GCP) for SAP workloads. S/4HANA Cloud uses HANA Cloud. Integration: Applications (ABAP, Java, etc.) connect to HANA via standard drivers (e.g. ODBC, JDBC). SAP applications are built to use HANA-specific features (e.g. CDS with HANA optimisations). Reporting tools (SAC, BW, Datasphere) can connect to HANA calculation views or tables. See Module 26 (Basis) for application-database relationship and Module 30 for S/4HANA.

Example: Why S/4HANA needs HANA

S/4HANA uses a universal journal (table ACDOCA) that stores all FI and many CO postings in one columnar table. Reports that aggregate by account, cost centre, profit centre, or time run directly on this table without copying data to an external BW cube first. In ECC on a traditional database, such reporting would often be slow or require pre-aggregation in BW. With HANA’s column store and in-memory speed, S/4HANA can offer “real-time” reporting on the same data as transactions. Similarly, material ledger and inventory reporting in S/4HANA rely on HANA for fast multi-dimensional queries. The simplification of the data model (e.g. removing redundant indexes and aggregate tables) is possible because HANA can answer complex queries on the single source table quickly.

HANA is the database and platform that S/4HANA and others run on.

Q4: What is a calculation view in HANA?
