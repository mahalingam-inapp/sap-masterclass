Module 32: Governance, Risk & Compliance (GRC)

For beginners: SAP GRC (Governance, Risk, and Compliance) is a suite that helps companies stay compliant and manage risk. It sits on top of your ERP and security: instead of only defining who can do what (that is Security, Module 27), GRC monitors whether users have conflicting access (e.g. one person creating vendors and also approving payments—a SOD violation), runs access reviews (recertification), and manages risk and controls (e.g. for SOX, internal audit). Key components: Access Control (SOD, user provisioning, emergency access), Process Control (control monitoring, compliance), and Risk Management. GRC can run on‑premise or in the cloud and integrates with S/4HANA (reads users and roles).

SAP GRC addresses governance, risk, and compliance across the enterprise. It complements Security (Module 27) by adding risk analysis, access reviews, control monitoring, and audit support. Many organizations use GRC to satisfy regulatory requirements (e.g. Sarbanes-Oxley, SOX) and internal audit.

Purpose and scope

GRC ensures that access and processes are governed (policies, roles, approval workflows), risks are identified and mitigated (access risk, process risk), and the organization remains compliant with regulations and internal controls. Scope includes: Access Control: Segregation of duties (SOD), compliant user provisioning, enterprise role management, risk analysis and remediation, superuser privilege management (e.g. firefighter), and access recertification. Process Control: Control framework (policies, control objectives), control monitoring (automated and manual tests), and compliance reporting. Risk Management: Risk identification, assessment, mitigation plans, and risk reporting. Audit Management: Audit planning, workpapers, findings, and follow-up (included in some GRC deployments). GRC aligns with the Three Lines of Defense (1st: operations; 2nd: risk/compliance; 3rd: internal audit).

In plain terms: Security (SU01, PFCG) defines roles and authorizations. GRC asks: “Do those roles create risks?” (e.g. one role that can both create a vendor and post payments = SOD risk.) GRC runs risk reports, supports access reviews (“recertify this user’s access every 90 days”), and tracks controls so that auditors and compliance teams have evidence that the organization is in control.

Features in detail

  • Access Control — SOD (Segregation of Duties): SOD rules define conflicting permission combinations (e.g. “create vendor” + “post payment” = critical risk). GRC reads users and roles from S/4HANA (and other systems), runs risk analysis, and flags users with SOD violations. Remediation: remove one of the roles, add mitigation (compensating control), or accept risk with approval. Rules can be delivered by SAP (rule set) or customized.
  • Access Control — Compliant User Provisioning: Workflow-driven user provisioning: request access → approval → provisioning in target systems (S/4HANA, SuccessFactors, etc.). Reduces “grant everything” and ensures access is approved and documented.
  • Access Control — Enterprise Role Management: Design and maintain roles (including from S/4HANA PFCG) in a central place; simulate risk before role is activated; transport or push roles to connected systems.
  • Access Control — Superuser Privilege Management (e.g. Firefighter): Restrict use of powerful access (e.g. SAP_ALL or critical transactions). Users request temporary “firefighter” access; usage is logged and time-limited. Reduces standing superuser IDs.
  • Access Control — Access Recertification: Periodic review of user access (e.g. quarterly). Managers or owners recertify “this user still needs these roles”; revoke if not. Evidence for auditors.
  • Process Control: Define control objectives and controls (e.g. “Vendor master change is approved”). Link controls to risks. Run control tests (automated: e.g. “no payment over X without two approvals”; manual: checklist). Document results and exceptions. Report on control effectiveness and compliance status.
  • Risk Management: Risk catalog (e.g. “Unauthorized payment”); assess likelihood and impact; define mitigation; track actions. Can link to Process Control (control mitigates risk) and to Access Control (access risk).
  • Audit Management: Plan audits; create audit workpapers; record findings and recommendations; track remediation. Integrates with Process Control and Risk Management for a full audit trail.

Data plane and control plane

Data plane: GRC stores its own data: risk analysis results (users with SOD violations), role and user snapshots from connected systems, control test results, risk registers, audit workpapers. Data is read from S/4HANA (and other systems) via connectors (RFC, API) for analysis; GRC does not replace S/4HANA’s user/role tables—it analyzes them. Control plane: GRC configuration: connection to S/4HANA (and other systems), SOD rule set, control framework, workflow and approval config, recertification cycles. Access to GRC itself is controlled by GRC roles (e.g. GRC Admin, Risk Analyst, Approver). See Module 1 for data vs control plane.

Deployment and integration

Deployment: SAP GRC can run on‑premise (GRC 12.0 and later, on NetWeaver; often on a dedicated GRC system or shared with BW) or in the cloud (SAP offers cloud editions of Access Control and Process Control; roadmap varies by region). Hybrid: GRC on‑prem connected to S/4HANA Cloud or to cloud applications. Integration: GRC connects to S/4HANA (and ECC, BW, SuccessFactors, Ariba, etc.) to read users, roles, and authorizations; to run risk analysis; and (with Access Control) to provision users or push roles. Connectors use RFC, OData, or product-specific APIs. Identity (e.g. IAS) can integrate for SSO and user sync. GRC feeds compliance and audit reports; data can be exported to BI or Audit Management.

Example: SOD violation and remediation

Company policy: the same person must not be able to create or change a vendor and post payments (SOD).

  1. Risk analysis: GRC Access Control runs a risk analysis (e.g. daily or on demand). It reads all users and their roles from S/4HANA. Rule set says: “Role with transaction X (vendor maintenance) + Role with transaction Y (payment posting) = SOD risk.” User JOHN has both roles → flagged as SOD violation (e.g. “Critical”).
  2. Remediation options: (a) Remove one role from JOHN (e.g. remove payment posting; only procurement keeps vendor maintenance). (b) Mitigate: document a compensating control (e.g. “All payments over 10k require second approval”) and accept residual risk with manager sign-off. (c) Emergency: grant temporary firefighter for one task, with log.
  3. Recertification: In the next access review cycle, JOHN’s manager sees JOHN’s roles and the SOD finding. Manager recertifies “JOHN still needs vendor maintenance” but revokes “payment posting” → violation cleared. GRC stores the review and decision for audit.

Result: SOD risk is identified, remediated, and documented. Process Control can define a control “SOD for vendor and payment is monitored and remediated”; evidence comes from GRC reports and recertification history.

Key tables and integration points

GRC uses its own repository (e.g. GRC backend tables for rules, analysis results, workflow, controls). It does not replace S/4HANA tables like USR02 or AGR_*; it reads them via connectors. Key integration: S/4HANA (or ECC): RFC or API connection; GRC pulls user master, role assignments, and (optionally) authorization data for risk analysis. User provisioning: GRC can create or change users in S/4HANA via BAPI or API when a request is approved. Process Control: Connectors to S/4HANA (or other systems) for automated control tests (e.g. “read payment documents and check approval”).

Important T-codes and Fiori apps (on‑prem GRC)

On‑premise GRC Access Control uses transactions such as GRAC_SPRO (GRC customizing), GRAC_USER_RISK_ANALYSIS (risk analysis for users), GRAC_ROLE_RISK_ANALYSIS (risk for roles), and Fiori apps (e.g. “Manage Access Risks,” “Manage User Access,” “Access Request”). Process Control and Risk Management have their own work centers and apps. Cloud GRC uses web UIs and Fiori-style apps in the GRC cloud tenant. Consult SAP Help for the current list of transactions and apps for your GRC version.

📝 Module Quiz

Question 1: What is the main purpose of SAP GRC Access Control in relation to Security (Module 27)?

  • A) Replace SU01 and PFCG
  • B) Analyze access for risks (e.g. SOD), run recertification, and govern provisioning
  • C) Only create users
  • D) Only run reports
Correct Answer: B
Access Control analyzes users and roles for SOD and other risks, supports access recertification, and can govern user provisioning. It does not replace Security; it adds governance and compliance on top.

Question 2: What does SOD mean in GRC?

  • A) Same order date
  • B) Segregation of Duties—preventing one person from having conflicting permissions (e.g. create vendor and post payment)
  • C) Only a table name
  • D) Only a report
Correct Answer: B
SOD = Segregation of Duties. GRC uses rule sets to identify users who have conflicting authorizations and supports remediation and recertification.

Question 3: Which GRC component focuses on control monitoring and compliance tests?

  • A) Only Access Control
  • B) Process Control
  • C) Only Risk Management
  • D) Only Basis
Correct Answer: B
Process Control manages the control framework, control objectives, and control tests (automated and manual) for compliance reporting.

Question 4: How does GRC typically get user and role data from S/4HANA?

  • A) By replacing S/4HANA tables
  • B) Via connectors (RFC, API)—GRC reads users and roles from S/4HANA for risk analysis
  • C) Only manually
  • D) Only from FI
Correct Answer: B
GRC connects to S/4HANA (and other systems) via RFC or APIs to read user and role data. It analyzes that data for risks; it does not replace the source system’s user/role tables.
