Module 35: Master Data Governance (MDG)

For beginners: In SAP, master data (e.g. material, vendor, customer, G/L account) is created and changed in the application modules (MM, FI, SD). When many people or many systems can change it, you get duplicates, inconsistencies, and poor data quality. SAP MDG (Master Data Governance) centralises master data creation and change with workflow and approval: a request to create or change a vendor goes through a process (validation, approval); once approved, the system creates or updates the master record in S/4HANA (and optionally in other systems). MDG also supports data quality (e.g. duplicate check, enrichment) and consolidation (merge master data from multiple sources). Key terms: governance, change request, activation, data quality.

SAP MDG provides governed, workflow-driven master data management. It is used when you need a single place to create and change master data with approval, auditability, and consistent quality. MDG can run on the same S/4HANA system (embedded) or on a separate MDG system that replicates to other systems.

Purpose and scope

MDG covers: Governed master data: Create and change master data (e.g. material, vendor, customer, G/L account, cost center) via change requests. Request goes through validation and workflow (e.g. approver); on release, data is activated (written to the active area and to consuming systems). Data model: MDG uses a flexible data model (entity types, attributes, relationships) that can extend standard S/4HANA master data. Data quality: Duplicate check (e.g. “similar vendor already exists”), enrichment (e.g. address validation, tax number check), and quality rules. Consolidation: Collect master data from multiple source systems (e.g. several ERPs), match and merge, and publish golden records to target systems. Central governance: One process for “create vendor” or “change material” across the group; full history and audit trail.

In plain terms: Without MDG, anyone with the right role can create a vendor in MM (transaction XK01) and the record is live immediately. With MDG, they submit a change request (“new vendor ABC, address, bank, etc.”). The request is validated (e.g. duplicate check); then it goes to an approver. When the approver releases it, MDG activates the data—the vendor is created in S/4HANA (and optionally in Ariba, SuccessFactors, etc.). So you have one controlled process and a clear audit trail of who requested and who approved.

Features in detail

  • Change request (CR): A change request is the container for create or change. User fills in the master data (e.g. vendor name, address, company code data). CR can be “in process” or “released.” Validation runs on save (e.g. mandatory fields, format). Workflow can be multi-level (e.g. requestor → department head → master data owner). On release, activation creates or updates the active record.
  • Activation: Activation writes the change request data to the active master data (e.g. LFA1, LFB1 for vendor). In distributed landscapes, replication (e.g. via ALE/IDoc or API) sends the new or changed record to other systems. So one approval flows to all systems that need the master.
  • Data quality: Duplicate check: before creating a vendor, MDG can search for similar existing vendors (e.g. by name, address) and warn or block. Enrichment: call external services (e.g. address validation, tax ID verification) and propose or fill fields. Quality rules can block activation until certain conditions are met.
  • MDG domains: SAP delivers MDG for several domains: Material, Vendor, Customer, Financial (G/L account, cost center, profit center, etc.), and custom (extensible). Each domain has a data model, UI (Fiori or Web UI), and workflow.
  • Consolidation (MDG-C): In consolidation scenario, master data is loaded from source systems (e.g. multiple ERPs). MDG matches records (e.g. “vendor X in system A = vendor Y in system B”), merges them into a golden record, and distributes the golden record back to targets. Used in group-wide master data harmonisation.

Data plane and control plane

Data plane: MDG stores change requests and staging data (the “draft” before activation). Active master data lives in the same S/4HANA tables as without MDG (e.g. LFA1, MARA); activation writes to them. In consolidation, MDG has its own consolidation repository and golden records. Control plane: MDG configuration: data model (entity types, attributes), workflow (steps, agents), validation rules, duplicate check config, replication (outbound to which systems). See Module 1.

Deployment and integration

Deployment: MDG can run embedded in S/4HANA (same system; change requests and activation in one box) or on a separate MDG system (central MDG that replicates to one or more S/4HANA or ECC systems). S/4HANA Cloud supports MDG for certain domains (e.g. business partner, material) with predefined scope. Integration: With S/4HANA: activation writes to local tables; with other systems: replication via ALE/IDoc, API, or CPI. MDG can also consume data from data quality or enrichment services (e.g. external address validation).

Example: Create vendor via MDG change request

Procurement needs a new vendor “Global Supplies Inc.” with address and bank details.

  1. Create change request: User opens “Create Vendor” (MDG Fiori app or Web UI). Enters general data (name, address, country, tax number) and company code data (payment terms, reconciliation account). Saves as change request. System runs duplicate check: “Vendor with similar name exists (ID 100001)—possible duplicate?” User confirms “new vendor”; request continues.
  2. Workflow: Change request is submitted. Workflow sends task to “Master Data Approver.” Approver reviews data, checks that bank account and reconciliation account are correct, and releases the request.
  3. Activation: On release, MDG activates the vendor: records are written to LFA1 (general), LFB1 (company code), and bank data. Vendor number (e.g. 100002) is assigned. If replication is configured, the new vendor is sent to Ariba or another system. Request is completed; audit log shows who created and who approved.

Result: One governed process, no direct creation in XK01; duplicate check and approval ensure quality and traceability.

Key MDG concepts

Term / ConceptPurpose
Change request (CR)Container for create/change of master data; goes through validation and workflow.
ActivationWriting CR data to active master data (and optionally replicating to other systems).
Data qualityDuplicate check, enrichment, quality rules to ensure consistent and correct master data.
ConsolidationCollect from multiple sources, match/merge, publish golden record to targets.
MDG domainScope of master data: e.g. Material, Vendor, Customer, Financial (G/L, cost center).
Relationship to MM, SD, FI: Those modules own the “active” master data (e.g. vendor in LFA1, material in MARA). MDG does not replace them—it adds a governed process for creating and changing that data. You can still create master data directly in the application (e.g. XK01) if allowed by policy; MDG is for when you want central governance, approval, and quality checks.

Key tables and Fiori apps

MDG uses staging tables for change request data and standard master data tables (LFA1, MARA, etc.) for active data. Fiori apps: “Create Vendor,” “Create Customer,” “Create Material,” “Manage Change Requests,” etc. T-codes depend on domain (e.g. MDG workflow monitor). See SAP Help for MDG.

📝 Module Quiz

Q1: What is the main benefit of MDG over creating master data directly in MM/FI/SD?

  • A) Only faster posting
  • B) Governed process with workflow, approval, duplicate check, and audit trail
  • C) Only more modules
  • D) Only reporting
Correct: B
MDG adds workflow, validation, and approval so that master data is created in a controlled way with full traceability.

Q2: What happens when a change request is “released” in MDG?

  • A) Only an email is sent
  • B) Data is activated—written to active master data (e.g. LFA1) and optionally replicated to other systems
  • C) Only deleted
  • D) Only locked
Correct: B
Release triggers activation: the change request content becomes the active master record.

Q3: MDG consolidation is used for:

  • A) Only posting documents
  • B) Collecting master data from multiple source systems, matching/merging, and publishing golden records
  • C) Only production orders
  • D) Only deliveries
Correct: B
Consolidation harmonises master data across multiple systems into a single golden record.

Q4: Which master data domains does MDG support (among others)?

  • A) Only FI document
  • B) Material, Vendor, Customer, Financial (G/L, cost center)
  • C) Only sales order
  • D) Only purchase order
Correct: B
MDG supports these and other domains; each has a data model and workflow.
