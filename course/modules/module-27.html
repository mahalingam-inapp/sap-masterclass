Module 27: Security & Authorization

For beginners: SAP Security ensures who can do what. In ERP you create users (SU01) and assign roles (PFCG). Each role contains authorizations—e.g. “user can display documents in company code 1000” or “user can post in company code 2000.” When a user runs a transaction, the system checks these authorizations; if something is missing, the transaction fails and SU53 can show which authorization was required. This is control plane: the same tables and programs are protected by these checks. In cloud products, identity and permissions are managed in admin UIs and often IAS (Identity Authentication Service). Key terms: user, role, authorization object, PFCG, SU53.

SAP Security covers user management, roles, and authorizations. It is part of the control plane; the data plane is protected by authorization checks at runtime.

Purpose and scope

Security ensures least privilege: users see and do only what they need. Key areas: User master (SU01): User ID, logon data, roles (or composite roles), and locks. Role design (PFCG): Role = set of transactions/reports and authorizations. Authorization object (e.g. F_BKPF_BUK) has fields (company code, activity); role gets specific values (e.g. 1000, 01). Composite role: Groups single roles for easier assignment. SOD (segregation of duties): Conflict checks so one user does not have incompatible permissions (e.g. create vendor and post payment). Audit: Logs and reports for compliance. HCM can drive role assignment by position (position-based access).

Features in detail

  • User (SU01): Create user; assign one or more roles. Optional: validity, address, default logon client. Lock user for security (e.g. leave) or unlock.
  • Role (PFCG): Create role; add menu (transactions, reports); generate authorizations from menu or maintain manually. Authorization object values (e.g. company code, plant) restrict scope. Save and transport role.
  • Authorization object: Technical object (e.g. S_BUKRS for company code, F_BKPF_BUK for FI document) with fields. Program/transaction checks this object; user must have a role that grants the required value combination.
  • SU53: After an authorization failure, user (or admin) runs SU53 to see which object and which field value caused the failure. Used to fix missing authorizations.
  • Cloud (IAS, product admin): SuccessFactors, Ariba, etc. use their own admin for users and permissions (e.g. RBP in SuccessFactors). IAS provides central identity and SSO (Module 22).

Data plane and control plane

Data plane: Authorization checks read user’s roles and authorizations (USR02, AGR_*, AUTH tables) at runtime; they do not store business data. Control plane: User master, roles, and authorization values are configuration; they govern who can access what. See Module 1.

Deployment and integration

Deployment: On‑premise: SU01, PFCG in each system. S/4HANA Cloud: user and role management in Fiori or admin. Integration: Identity can be federated (e.g. IAS, corporate IdP); roles can be derived from HCM position. GRC (Governance, Risk, Compliance) tools for SOD and access control.

Example: Role for FI accountant (display only, company code 1000)

New accountant should see FI documents and G/L balances for company code 1000 only; no posting.

  1. Create role (PFCG): Create role “Z_FI_ACCOUNTANT_DISPLAY.” Add menu: FB03 (display document), S_ALR_87012284 (G/L balance), and similar display transactions. Restrict to company code 1000 in authorization object S_BUKRS (and F_BKPF_BUK, etc.). Generate authorizations; maintain manually if needed (e.g. only display activity 03). Save.
  2. Assign to user (SU01): Open user; assign role Z_FI_ACCOUNTANT_DISPLAY. User logs on and has only these transactions with company code 1000. If user tries FB01 (post), authorization check fails.
  3. Troubleshooting (SU53): If user gets “Authorization failure” when opening a report, user runs SU53: system shows missing authorization (e.g. object F_BKPF_BUK, field BUKRS = 1000, ACTVT = 03). Admin adds this to the role or creates a new role and assigns it.

Result: User has least privilege; audit trail of who can do what.

Key concepts

Authorization object: Technical object with fields (e.g. company code, activity). Transaction checks it; user must have a role granting the required values. Composite role: Bundle of single roles; assign once to user. SOD: Segregation of duties—prevent conflicting permissions (e.g. create vendor + approve payment). SU53: Use after “Authorization failure” to see which object/field failed and fix the role.

📝 Module Quiz

Q1: PFCG is used for:

  • A) Sales order
  • B) Role design (profile generator)
  • C) Only MM
  • D) Only FI posting
Correct: B
PFCG = Profile Generator for roles and authorizations.

Q2: SU53 shows:

  • A) Purchase order
  • B) Authorization check failures (why access was denied)
  • C) Only delivery
  • D) Only invoice
Correct: B
SU53 = display authorization check log (useful for troubleshooting).

Q3: Authorization object controls:

  • A) Only material
  • B) What a user can do (e.g. which company code, which activity)
  • C) Only vendor
  • D) Only customer
Correct: B
Authorization objects define fine-grained access (e.g. company code, activity).

Q4: What is SOD in security?

  • A) Only a table
  • B) Segregation of duties—preventing conflicting permissions (e.g. create vendor and post payment)
  • C) Only a report
  • D) Only a transaction
Correct: B
SOD = Segregation of Duties; reduces fraud and error risk.
