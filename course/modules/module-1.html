Module 1: Foundation concepts

For beginners: If you are new to SAP, think of this module as learning the “map” before visiting the “cities.” SAP has many products (ERP for finance and logistics, cloud apps for HR and procurement, and a platform for integration). To avoid getting lost, we use four ideas everywhere: data plane (where business data lives and is processed), control plane (where we configure, secure, and connect systems), deployment (where the system runs: your data center or the cloud), and integration (how systems talk to each other). Once you understand these, every later module will make more sense.

This chapter establishes the shared concepts used across all SAP modules and products. Every later chapter (Modules 2–31) will refer back to these ideas. Understanding them once here will make it much easier to see how each solution fits into the bigger picture.

Why these concepts matter

In any SAP landscape—whether you have only one S/4HANA system (SAP’s current ERP suite, the successor to ECC) or a mix of S/4HANA, cloud products, and BTP (SAP Business Technology Platform, used for integration and extensions)—two questions always apply: Where does the business data live and get processed? (data plane) and Where do we configure, secure, and connect systems? (control plane). Deployment choices (on‑premise, cloud, hybrid) and integration patterns (APIs, middleware, events) determine how you run and connect these pieces.

In plain terms: Imagine a company: the data plane is like the filing cabinets and the work done on the documents (invoices, orders, payments). The control plane is like the rules (who can access which cabinet, how documents are filed, and how different departments send documents to each other). Using this vocabulary avoids confusion when you move from Finance (FI) to HR cloud (SuccessFactors) to integration (CPI).

Data plane

Definition: The data plane is where business data is stored, processed, and transacted. It holds the operational and analytical data that applications read and write—for example, sales orders, purchase orders, invoices, and general ledger entries. It does not include the “where and how” of configuration or security; that belongs to the control plane.

In plain terms: Whenever you create, change, or read a business record (an invoice, a customer order, an employee record), you are touching the data plane. The data plane is the “what happened” and “what is the current state”; the control plane is the “how we allowed it” and “how we set it up.”

Data plane in SAP ERP / S/4HANA

In an on‑premise or hosted ERP system, the data plane consists of:

  • Storage: The database (SAP HANA in S/4HANA, or legacy databases in ECC) holds all application tables. Each SAP module uses specific table names: for example, FI (Finance) stores document headers in BKPF and line items in BSEG; MM (Materials Management) stores purchase orders in EKKO/EKPO and material documents in MKPF/MSEG; SD (Sales & Distribution) stores sales orders in VBAK/VBAP and delivery data in LIKP/LIPS. You do not need to memorize these now—just know that each module has its own set of tables, and they all live in the same physical database.
  • Processing: The application servers (running ABAP, SAP’s main programming language, and optionally Java) execute business logic: validations, calculations, document creation, and postings. When a user posts a goods receipt in MM, the program reads the purchase order, creates material document records (that is data plane), and may trigger a posting to FI (again, data plane). In that moment, no configuration or user management is changed—only business data is read and written.

So for ERP, the data plane = database + application server executing transactions and reports.

Data plane in SAP cloud products

In SAP SuccessFactors (HR), Ariba (procurement), Concur (expenses), SAP Analytics Cloud, and similar products, you do not have direct access to database tables like in ERP. Instead:

  • Data is stored in SAP‑operated (or partner) data centers as entities—logical objects such as User, Employee, Position, Goal in SuccessFactors; Purchase Order, Invoice in Ariba; Expense Report in Concur. You cannot run SQL against them; you work with the product’s own data model.
  • You access and change this data through UIs (the product’s screens and apps) and APIs (OData, REST—standard ways for applications to exchange data). Replication or integration may copy data to S/4HANA or Datasphere, so the same information may exist in more than one place; the source of truth for each product is still in its own cloud tenant (your dedicated instance of that product).

So for cloud products, the data plane = tenant data (entities) + product application layer; you interact via UIs and APIs, not SQL.

Data plane in SAP Datasphere and BW

In SAP Datasphere (cloud) and SAP BW/4HANA (on‑premise or cloud), the data plane is the semantic layer and stored datasets: views, persisted tables, and models that consolidate data from ERP and other sources for reporting and analytics. SAC (SAP Analytics Cloud) then connects to these as data sources. So the data plane for analytics = Datasphere/BW objects + data stored there.

Takeaway: For any module or product, ask: Where is the business data stored, and where is it processed? That is the data plane for that solution.

Control plane

Definition: The control plane is where system behavior is configured, orchestrated, and governed. It does not hold day‑to‑day business transactions (those are in the data plane); it defines how the system runs, who can do what, and how systems connect to each other.

In plain terms: The control plane is where administrators and consultants set the rules: which company codes exist, which document types are allowed, which users have access to which transactions, and how data is sent to or received from other systems. Changing the control plane does not create a new invoice or order—it changes how future invoices and orders will be created and who can do it.

Control plane in SAP ERP / S/4HANA

  • Basis / system administration: Client, instance, application server profile, transport (STMS), patches, and upgrades. This defines which systems exist and how they are maintained.
  • Configuration (customizing): SPRO (transaction for the Implementation Guide / IMG) and related configuration tables (e.g. company code in T001, purchasing group in T024) define company codes, plants, document types, account determination—i.e. how the data plane behaves (which accounts are used, which number ranges, etc.).
  • Security: Users (SU01), roles (PFCG), and authorizations control who can access which transactions and data. A user without the right role cannot post an FI document even though the data plane is ready to store it.
  • Integration configuration: RFC destinations (SM59), OData/Gateway setup, and (when used) PI/PO or CPI connection details control how data flows between this system and others.

Control plane in SAP BTP

BTP is largely a control plane for the broader landscape:

  • Global account and subaccounts: Entitlements and quotas define which services (Integration Suite, Datasphere, ABAP environment, etc.) are available and in which region.
  • Identity (IAS): Central identity and authentication for SAP and non‑SAP apps; single sign‑on and federation so users do not log in separately to each product.
  • Integration Suite: CPI (Cloud Integration) flows, API Management policies, and Event Mesh topics/subscriptions control how S/4HANA and cloud products exchange data.

Extensions and apps that run on BTP (e.g. an ABAP Cloud app or a Cloud Foundry app) may have their own small data plane (e.g. app-specific tables), but BTP itself is the place you go to manage integration and extension, not to store core business transactions.

Takeaway: For any module or product, ask: Where is configuration, identity, and integration routing managed? That is the control plane.

Deployment

Deployment defines where and how a solution is run: in your data center (on‑premise), in SAP’s cloud, or a combination (hybrid). This affects who operates the system, who applies upgrades, and how you connect to other systems. As a beginner, it is enough to know: same SAP product (e.g. S/4HANA) can run at your site or in SAP’s cloud; cloud products (SuccessFactors, Ariba, etc.) run only in the cloud.

Integration

Integration is about connecting systems so that data and processes flow correctly—for example, sending employee data from SuccessFactors to S/4HANA, or sending an invoice from Ariba to FI. The design of these connections (which system talks to which, which protocol, which mapping) is part of the control plane; the actual flow of data uses the data planes of the connected systems.

In plain terms: When one system needs to send data to another (e.g. “create an FI document when an invoice is approved in Ariba”), someone configures an integration flow (e.g. in SAP CPI on BTP). That configuration is control plane; the invoice in Ariba and the resulting document in S/4HANA are data plane.

Example: How does a vendor invoice get from Ariba to S/4HANA FI?

  1. Control plane (BTP): An integration flow (iFlow) in SAP CPI is configured to listen for “invoice created” from Ariba and to call S/4HANA’s API (or IDoc) to create an FI document. Security (credentials, certificates) is also configured in BTP/CPI.
  2. Data plane (Ariba): The invoice exists in Ariba as an entity; when it is submitted, Ariba sends the payload to CPI (outbound).
  3. Data plane (S/4HANA): CPI calls S/4HANA; the application server creates a document in BKPF/BSEG (and possibly MM for the purchase order reference). The data now lives in the ERP data plane.

So: control plane = the CPI flow and its configuration; data plane = the invoice in Ariba and the FI document in S/4HANA.

Key integration patterns you will see in later modules:

  • Within ERP (same system): Document flow, automatic postings, and shared master data (e.g. FI–MM–SD–CO). No middleware needed—just function calls and shared tables.
  • ERP ↔ cloud: SAP CPI (iFlows), OData/REST/BAPIs, IDocs/RFC, SAP Event Mesh. The control plane (CPI, API Management, Event Mesh) is often on BTP.
  • Cloud to cloud: Often via BTP (e.g. SuccessFactors ↔ S/4HANA for employee data; Ariba ↔ S/4HANA for P2P; Concur ↔ S/4HANA for expense posting).
  • Analytics: Datasphere and SAC connect to S/4HANA, BW, and cloud products via connectors and APIs; data is replicated or accessed live for reporting.

📝 Module Quiz

Question 1: What is the data plane?

  • A) Where systems are configured and secured
  • B) Where business data is stored and processed
  • C) The SAP cloud only
  • D) The same as the control plane
Correct Answer: B
The data plane is where business data is stored and processed (e.g. ERP tables and application server, or cloud entities and APIs).

Question 2: Which is part of the control plane in ERP?

  • A) Transaction tables like BKPF
  • B) Basis, customizing (SPRO), and security (users/roles)
  • C) Only SAP BTP
  • D) Cloud tenant data
Correct Answer: B
Basis, customizing, and security (users, roles, authorizations) are control plane—they govern how and who accesses the system.

Question 3: How do SAP cloud products (e.g. SuccessFactors, Ariba) deploy?

  • A) On‑premise only
  • B) SaaS only—tenant, region, connectivity
  • C) Same as S/4HANA on‑prem
  • D) Only via BTP ABAP
Correct Answer: B
Cloud products are SaaS only; customers get a tenant and configure via admin UIs and APIs; connectivity to S/4HANA and BTP is key.

Question 4: In a hybrid landscape, where is the integration flow (e.g. Ariba → S/4HANA) typically designed and run?

  • A) Only inside the Ariba tenant
  • B) In SAP BTP (e.g. CPI) or on‑premise PI/PO
  • C) Only in S/4HANA Basis
  • D) Only in SuccessFactors
Correct Answer: B
Integration flows are part of the control plane and run in middleware: BTP (CPI) or on‑premise PI/PO.
